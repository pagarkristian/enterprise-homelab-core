## 📄 1. Executive Summary

> Two new features were added to the TechSecure employee portal: profile photo upload and direct payslip access by ID. Both work correctly for normal use, but both were built with mistakes that are easy to make under deadline pressure — the payslip page doesn't check whether the person asking actually owns the payslip, and the photo upload passes the filename straight into a system command without checking it first. Testing confirmed that any logged-in employee can read every other employee's salary, that the payslip's database query can be manipulated, and that a crafted filename can get executed as a command on the server. None of these were visible to our SIEM's default alerting, because every one of them produces a normal-looking, successful web request — the kind of request a security tool trained to spot *errors* has no reason to flag. Three custom detection rules were written and confirmed, through a cold retest, to catch all three attacks reliably while staying silent during normal use. The unrestricted file-extension upload path (e.g. uploading a `.php` file) was identified in code review but has not yet been exploited or tested, and remains an open item.
>

## 🚨 3. Findings

Fill in one row per weakness confirmed in v2.1.1 and v2.2.1. Use CVSS-style severity words (Critical / High / Medium / Low) based on actual impact, not how "cool" the bug sounds.

| # | Finding | Severity | Status Before Detection Rules | Status After (v2.3.1) |
|---|---|---|---|---|
| 1 | IDOR on `slip.php` — any logged-in user reads any other employee's payslip by changing the `id` parameter | **High** (broken access control; salary data of every employee exposed to every other logged-in employee) | Undetected — confirmed the request reached `access.log` with a 200 status, confirmed independently that Wazuh's default ruleset returned no alert for it | **Detected** — rule `100102` fires on the 3rd distinct `id` request from the same source within 60s. Confirmed on cold retest, zero false positives on a single normal view |
| 2 | SQL Injection on `slip.php` — `$id` concatenated directly into the SQL query, no prepared statement | **High** (unauthorized data read via a manipulated query; stacked/destructive queries not possible since the code uses `mysqli_query()`, not `multi_query()`, so the real-world impact is limited to reading, not destroying, data) | Undetected — same reason as above, status 200, nothing for a generic rule to flag | **Detected** — rule `100100` fires on injection-pattern keywords (`OR`/`UNION`/`SELECT`/`--`/quotes) in the URL. Confirmed on cold retest (36 hits across repeated submissions), zero false positives on normal payslip access |
| 3 | Unrestricted file upload on `upload-photo.php` — no extension or MIME-type check before saving the file | **Medium (unconfirmed severity)** — if an attacker could upload and then execute a `.php` file, this escalates to Critical (remote code execution), but that chain has not been exploited or tested | Not tested yet | Not tested yet — no detection rule exists for this specific path either, since nothing was confirmed to detect. **Open gap**, carried forward from v2.2.1/v2.3.1 |
| 4 | OS Command Injection via upload filename — the raw filename is concatenated into a `shell_exec()` call with no sanitization | **Critical** (arbitrary filename content reaches a shell; confirmed the shell splits the filename at `;` and attempts to execute what follows as a separate command) | Undetected — the ImageMagick failure in `error.log` has no Apache-style prefix, so it was never even decoded as a web event, let alone evaluated by a web-related rule | **Detected** — rule `100103` matches the `convert-im6` failure signature. Confirmed on cold retest, zero false positives on a normal upload. (Detects a side-effect of the attack, not the injection itself — see honest limitations in v2.3.0) |
| 5 | Directory listing enabled on `/profile_photos/` — every uploaded file is browsable | **Low** (information exposure; becomes more serious combined with finding 3, since an uploaded script would also be easy to find and access) | Undetected — not a web-application-logic issue a log-based rule naturally covers, and no rule was written to specifically flag directory-listing requests | **No rule written** — out of scope for the three rules built in v2.3.0. **Open gap**; the real fix is disabling directory listing in Apache config (see Recommendations), not a detection rule |

## 🛡️ 4. Recommendations

Detection (the three Wazuh rules) tells us *when* these attacks happen again — it does not fix the underlying code. Each finding still needs an actual remediation:

| # | Finding | Recommended Fix |
|---|---|---|
| 1 | IDOR on `slip.php` | Add an ownership check: before returning a payslip, verify the `id` requested belongs to the employee tied to the current session (e.g. `WHERE id = ? AND employee_id = ?` using the session's own employee ID), instead of trusting any `id` a logged-in session happens to send. |
| 2 | SQL Injection on `slip.php` | Switch to a prepared statement with a bound parameter, the same pattern `index.php` already uses for login (`mysqli_prepare()` / bound `?` placeholder) instead of string concatenation into the query. |
| 3 | Unrestricted file upload | Validate the file's actual content (not just the filename extension) — e.g. check the real MIME type/magic bytes with `finfo`, reject anything that isn't a genuine image, and store uploaded files outside the web-servable directory, or under a randomly generated name with no extension that would ever be executed. |
| 4 | OS Command Injection via filename | Never build a shell command by concatenating user-controlled input. Use a PHP image-processing library's native API (e.g. the `Imagick` PHP extension, or GD) to resize the image in-process instead of shelling out to `convert`. If shelling out is unavoidable, use `escapeshellarg()` on every user-controlled argument — but switching off `shell_exec()` entirely is the stronger fix. |
| 5 | Directory listing on `/profile_photos/` | Disable Apache's directory indexing for that path (`Options -Indexes` in the vhost config or a local `.htaccess`), so the folder's contents can't be browsed even if someone guesses the URL. |

> **Note:** the technical fixes above are standard remediation for these CWE classes and are safe to use as-is. What you should personalize before an interview is *how you'd prioritize them* — for example, which one you'd fix first given limited time, and why.

## 🎓 6. Lessons Learned

> **⚠️ Read before using:** this is the section an interviewer will probe hardest, because it's the one place a scripted answer falls apart under follow-up questions. What's below is a draft grounded in things that genuinely happened during this project — not invented — but you need to rewrite it in your own words and be ready to explain any of it live, unprompted, before it goes anywhere near a CV or interview.

**1. What surprised you during this exercise?**

> Draft: Every attack that actually worked — IDOR, SQLi, command injection — produced a perfectly normal HTTP 200 response. I expected attacks to look obviously "broken" in some way. Instead, the default Wazuh ruleset (which mostly reacts to error status codes like 4xx/5xx) had no reason to flag any of them, because nothing about the *traffic* looked wrong — the problem was entirely in what the *application* allowed a valid, successful request to do. That reframed security monitoring for me: a SIEM is only as good as the rules written for the specific application behind it, not just the infrastructure.
>
> Also specifically surprising: writing rule `100103` and having it silently never fire, even though the exact string I was matching on (`convert-im6`) was clearly sitting in the log file. Running `wazuh-logtest` directly instead of guessing showed the real reason — the log line had never been decoded as a web event at all (no Apache-style prefix), so my `<if_group>web</if_group>` condition excluded it before the match was ever tried. It was a reminder that a rule can be logically correct and still never fire, if an earlier assumption in it is wrong.

**2. What would you do differently if building this feature for a real company?**

> Draft: I'd involve security review before the feature reached "working in the demo" — both vulnerabilities came from reasonable-looking code a developer under deadline pressure would actually write (trusting a session without checking ownership, trusting a filename came through a real upload form without checking what's *in* the filename). I'd also write the detection rules at the same time as the feature, not months later as a separate phase — by the time I wrote rule `100102`, I already knew exactly what pattern to look for because I'd just attacked it myself, which isn't how it would work defending a feature I hadn't broken first.

**3. What's still a gap, even after the detection rules?**

> Draft: Several, and I'd say this plainly in an interview rather than oversell the project:
> - The unrestricted-upload-extension path (uploading a `.php` file) was never actually tested — it's a code-review finding only, not a confirmed exploit, and there's no detection for it either.
> - Rule `100100` matches literal SQL keywords, so a payload that avoids those exact words would slip through untouched — it's a signature, not real SQL-syntax understanding.
> - Rule `100102`'s 60-second/3-request threshold was tuned to match the exact test I ran, not derived from a real baseline of normal traffic; a slower scan (one request every few minutes) would stay under it indefinitely.
> - Rule `100103` only works because ImageMagick happens to log its own failure in a way I could match on — it detects a side-effect, not the injection itself. A payload that didn't make `convert` fail would leave no trace for this rule.
> - None of the three rules inspect POST request bodies at all, because Apache's `access.log` doesn't record them — anything submitted purely in a POST body would be invisible to every rule here.
> - Directory listing on `/profile_photos/` was confirmed but never got its own detection rule — it's a fix to apply (disable indexing), not something worth building a SIEM rule for.
